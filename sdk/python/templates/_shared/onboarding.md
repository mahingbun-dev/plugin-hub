## 什么叫「接入成功」

两件事，仅此而已：

1. **中台接受了你的注册**
2. **经中台真实调用一次，正常返回**

它被拆成**四道关**——不是因为流程繁琐，而是因为**每一关失败的原因和验证手段完全不同**，
混在一起看会让人无从下手。

## 四道关

| 关 | 验的是什么 | 怎么验 | 需要中台吗 |
|---|---|---|---|
| **L1 契约自洽** | manifest 与 proto 一致、至少声明一条契约、工具名合法 | 跑本工程的契约一致性测试 | 不需要 |
| **L2 运行时自检** | gRPC 起得来、Health/Describe 应答、空信封不崩 | `hubprobe conform <插件地址>` | 不需要 |
| **L3 中台接受注册** | 上报地址拨得通、契约兼容、版本/实例不冲突 | **启动插件，看它的日志** | 需要 |
| **L4 端到端调用** | 经中台 ingress 真实调用一次 | `hubprobe e2e <中台地址> <插件名>` | 需要 |

### ⚠️ 先记住这一句：L1、L2 全绿 ≠ 能接入

前两关验的是「**插件自己是否自洽**」。它们够不着最难的两件事：

- **中台能不能拨通你上报的地址**——这是**网络视角**的问题。你本机测自己通不通，
  证明不了中台拨得到（中台可能在另一台机器、另一个网段，中间还隔着 nginx）。
- **你的契约与已登记版本冲不冲突**——这要跟中台库里的**历史版本**比对，
  插件侧根本没有那份数据。

这两件事只有 **L3** 能答。**真正的分水岭在第 3 关。**

## 端口速查

先分清两件事：

- **谁在听**：中台的 HTTP 面与插件面是**中台**在听；插件端口是**你在听**。
- **站在哪看**：下表一律是**调用者视角**——你在自己的机器上敲什么。

| 端口 | 是什么 | 本地 | UAT（在开发机上） |
|---|---|---|---|
| **8092** | 中台 **HTTP 面**（ingress / admin / MCP） | `http://127.0.0.1:8092` | `https://hub.example.com:8081/hub-api` |
| **8093** | 中台 **插件面**（gRPC）——插件的 `HUB_ADDR` 指这里 | `http://127.0.0.1:8093` | `https://hub.example.com:8094` |
| **9000** | **插件自己**的监听端口——也是 `HUB_ADVERTISE_ADDR` 该指向的地方 | `:9000` | 同 |

> **两个环境不能换着用**。本地照 UAT 写 `127.0.0.1:8095` 会 `connection refused`——
> 那个端口只在 UAT 主机内部存在；反过来在开发机上把 UAT 写成 `127.0.0.1:8092`
> 连的是你自己机器。这一条踩起来最费时间，因为报错只有一句 connection refused，
> 看不出是端口问题。

**别猜，自己验一下**（探活不鉴权，这是最省事的自证动作）：

```bash
curl http://127.0.0.1:8092/health
# 真中台 → {"status":"ok","name":"anc-hub",...}
# mock   → {"status":"ok","name":"hub-mock",...}
```

看到 `connection refused` 是**端口**不对；`404` 或一段 HTML 是**前缀**不对。

## ⚠️ 最大的坑：`HUB_ADVERTISE_ADDR` 要写「中台视角」的地址

中台在注册时会**连你上报的地址做可达性探测**，探不通直接拒绝注册
（拒绝码 `UNREACHABLE`）。所以它必须是「从**中台那边**拨得通」的地址，
而不是本机视角的 localhost：

- 中台与插件同机 → `http://127.0.0.1:9000` 可以
- 中台在别的机器 → 必须写本机的内网 IP 或域名，例如 `http://203.0.113.10:9000`

**本机自测通了不算数**：你在本机连 `127.0.0.1:9000` 走的是回环，中台从它那边拨
不拨得到，这个动作根本验不出来。地址填错时 L1、L2 照样全绿，插件却在真实环境里
永远接不进来。

## 本地没有中台，怎么过 L3

用 `hub-mock`——中台仓库里的本地替身，一个进程、不需要数据库与 Redis，
绑的端口与真中台**相同**（8092 / 8093），所以插件的 `HUB_ADDR` 一个字都不用改：

```bash
cargo run -p hub-mock          # 在中台仓库根目录
curl http://127.0.0.1:8092/plugins     # 看在册的
curl http://127.0.0.1:8092/rejections  # 看被拒的，含原因与出路
```

⚠️ **先确认你打的是谁**。mock 与真中台绑同一组端口，而「注册成功了」这句日志
两者都会打——但它们能证明的东西不同：

```bash
curl http://127.0.0.1:8092/health
#   "name":"hub-mock"  → 你在对 mock 验
#   "name":"anc-hub"   → 你在对真中台验
```

`hub-mock` 与真中台**判据同源**（都调中台的注册校验函数），但它**不落库、不实现
HubState、不做心跳超时摘除**。所以涉及这三点的结论，在 mock 上不成立——
最后交付前要用真中台再走一遍 L3、L4。

## 被拒了怎么读原因

中台的拒绝是**结构化的**，而且 `message` 说**哪里错了**、`detail` 说**该怎么办**。
照 `detail` 做就行，不必猜：

```console
{"level":"ERROR","msg":"中台拒绝了注册","code":"UNREACHABLE",
 "message":"插件地址 http://127.0.0.1:9000 不可达",
 "detail":"...；请确认 advertise_addr 填的是中台视角下可达的地址（SDK 里是 HUB_ADVERTISE_ADDR）..."}
{"level":"ERROR","msg":"注册未通过，稍后重试","reasons":1,"retry_in":"5s"}
```

常见的几个码：

| 码 | 意思 | 多半是 |
|---|---|---|
| `UNREACHABLE` | 中台拨不通你上报的地址，或拨通了但你自报不健康 | `HUB_ADVERTISE_ADDR` 写成了中台拨不到的地址 |
| `MANIFEST_INVALID` | manifest 自身不合法 | 插件名含非法字符、缺版本号、声明的类型不在 descriptor 里 |
| `DESCRIPTOR_INVALID` | 提交的 descriptor 解析不了 | 传的不是 proto 编译产物 |
| `VERSION_CONFLICT` | 同版本号的契约或 manifest 变了 | 改了契约却忘了升版本号 |
| `BREAKING_CHANGE` | 相对基线有破坏性变更 | 删了字段、改了类型或编号。**升版本号不是出路**——按原编号原类型改回来 |
| `INSTANCE_CONFLICT` | `instance_id` 为空、超长，或已被**别的插件**占用 | 多个插件把 `HUB_INSTANCE_ID` 写成了同一个值 |

## 插件模型的几条约定

- **校验器先行**：中台一定先调 `Validate`，通过才调 `Handle`。校验不通过时
  `Handle` 不会被调用，链路当场短路。
- **强制无状态**：实例内存不保证跨调用保留（换来热切换零代价、可水平扩展）。
  需要跨调用保留的东西要走中台的状态接口。
- **契约不可漂移**：同一版本号的 manifest 与 proto 不可变更，改了请升版本号；
  中台会拒绝「同号不同契约」的注册。
- **预算来自信封**：信封带着绝对 deadline 逐跳递减。紧张时应提前放弃，
  而不是把时间耗光后靠上层超时兜底——那样调用方连「为什么慢」都看不出来。
